## What the skills get wrong

**attestation-analyst**
- **Missing evidence becomes a gap.** In 11 of 12 profiles, `assurance:none` is cited to the evidence listing ("EVIDENCE FILES: 0 files; STAGE-1-CHECKLIST §2"). Gold uses `assurance:none` once across all 23 cases. `hw:no-quote` is cited to "SUBJECT/INPUTS block only" (oauth3-burnt, talos, primus). The skill invites this: "If you need something you cannot fetch, say so as a gap with status `unknown`."
- **Stage is always 0.** The "fail any Stage 1 item → 0" rule, combined with the invented gaps above, means `~1` is never chosen. It is wrong on talos, tinfoil-containers and trustedrouter.
- **Code tags are over-applied** (chutes: `code:closed`, `code:image-unpinned`, `code:weights-unpinned`, `code:not-reproducible`, none in gold) while the gold `code:model-unbound` and `code:unmeasured-workload` are missed.

**formal-methods-reader**
- **It asserts deployment matches the proof without evidence.** On eth2-kevm: "the deployment runs that same bytecode, so the classic source/binary gap is closed". Gold: the guarantee is for solc 0.6.8 output and mainnet runs a 0.6.11 build. On eth2-vyper it described the verified artifact as Solidity, but it is a Vyper hotfix build that was never deployed.
- **It misses the bug location in the unverified edge.** verdi: `recv` not named. compcert: "middle-end" not named.

**pour-planning**
- No skill failure was observed. The tasks never need outside help, so the skill correctly declines to pour, and this corpus does not exercise steps 2–5 or the injection rule. It needs tasks the sealed model cannot solve alone, such as current regulations or methods it gets wrong on the floor.

**All three: reply format.** 9 sessions ended on an unparseable reply: targon and libcrux in the baselines; lunal, venice, trustedrouter and kevm in the re-runs; orchestrated pour t07 (twice) and t10 (once; it parsed on re-run). The causes were Python-dict quoting, two concatenated JSON objects, and a YAML-like list instead of JSON. With glm-5.3-flash a strict JSON-only output instruction would probably matter more than any content rule.

## Revisions and re-runs

Re-runs used the revised skills from commit c5a7e67, on the cases that failed: stage wrong, F1 < 0.4 or no parse for attestation; keyword recall < 0.8 or no parse for formal.

**attestation-analyst.** The revision said: missing evidence → `unknown` with no tag; never cite the inputs block or a listing; `hw:no-quote` and `assurance:none` only with a file showing them. **Reverted** in 8eb621a, manifest hash in 5408ee9. The revert commit message says 0.26 → 0.09; the exact figures are below.

| case | F1 before | F1 after |
|---|---|---|
| chutes | .22 | .15 |
| confer | .20 | .29 |
| talos | .44 | 0 (all axes `unknown`, 0 gaps) |
| tinfoil-containers | .43 | 0 (all axes `unknown`, 0 gaps) |
| targon | no parse | 0 |
| lunal, venice, trustedrouter | .38 / .18 / .36 | no parse |

The 4 cases that parsed both times went from 0.32 to 0.11. Stage was still `0` everywhere. On cases with no given files, the earlier "recall" came from generic tags that the gold happened to share. Honest `unknown` scores 0 there, because gold comes from a networked audit. The eval cannot separate a good no-evidence answer from a bad one until the analyst has the network or tools.

**formal-methods-reader.** The revision says: name the exact build on each side (commit/release, compiler version, build variant such as hotfix, config); never claim "same bytecode" from memory. **Kept**:

| case | recall before | recall after |
|---|---|---|
| eth2-vyper | .67 | .50; now "provenance (source commit, Vyper version, bytecode hash) is not traced in these inputs" and no Solidity confusion. Lost the keyword `solidity`. |

| eth2-kevm | .67 | no parse |

The intended behavior change appears in both parsed outputs, but keyword recall does not reward it, and names_gap needs the judge. Read as inconclusive at n=2.

**pour-planning.** Not revised: no failure was attributable to the skill. Other agents also changed it after d397943 (7562496, b0f8b9f).
